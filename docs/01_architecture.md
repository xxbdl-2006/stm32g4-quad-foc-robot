## 二、数据流与频率预算

| 方向 | 内容 | 频率 | 帧长 | 带宽 |
|---|---|---|---|---|
| 板 → PC | 关节反馈 `CLS_FAST(0..3)` | 200 Hz × 4 | 8 B | 640 帧/s |
| 板 → PC | 板级状态 `CLS_FAST(4)` | 200 Hz | 8 B | 200 帧/s |
| 板 → PC | 心跳 `CLS_HEARTBEAT` | 10 Hz | 8 B | 10 帧/s |
| 板 → PC | 气泵状态 `CLS_IO(1)` | 50 Hz | 8 B | 50 帧/s |
| 板 → PC | 相机同步 + 四关节锁存 `CLS_IO(3,5..8)` | 30 Hz | 5×8 B | 150 帧/s |
| PC → 板 | 四关节位置指令 `CLS_MOTION` | 100 Hz × 4 | 8 B | 400 帧/s |

合计峰值约 **1450 帧/s**。1 Mbps 下每帧含仲裁+CRC+位填充约 130 bit，
即约 **190 kbit/s**，总线占用率 **19%**。剩下的余量可以再加 2 个扩展板。

CAN 的优先级仲裁是"ID 数值小者优先"。本协议 ID 高 3 位是节点号，
因此 **NODE_HOST(0) 的指令帧天然优先于 NODE_MAINBOARD(1) 的反馈帧** ——
这正是我们想要的：指令的时效性比反馈重要。参数帧走 `CLS_PARAM`(0x3)，
ID 比 `CLS_MOTION`(0x2) 大，所以不会堵住位置指令。

## 三、实时性关键路径

### 3.1 电流环（50 µs 预算）

| 步骤 | 耗时 @170MHz |
|---|---|
| ADC 注入组转换（4 通道 × 3 路并行） | 1.4 µs |
| 四个关节的编码器采样（流水线，1 帧/片） | 6.4 µs |
| Clarke + Park ×4（含 CORDIC） | 2.1 µs |
| PI ×8 + 矢量限幅 ×4 | 2.4 µs |
| 反 Park + SVPWM ×4 | 1.3 µs |
| CAN 帧入 TX FIFO（平均 0.15 帧/周期） | 0.4 µs |
| **合计** | **≈14 µs（28%）** |

余量 72%，足够再加一层观测器或自适应算法。

### 3.2 CAN → ROS 的延迟

```
驱动板写 TX FIFO  →  CAN 控制器仲裁发送   →  USB-CAN / 内核驱动
       0 µs              ~130 µs @1Mbps          20~80 µs
   →  socket 接收缓冲   →  rx_thread 解析  →  flush 定时器聚合  →  话题发布
         <10 µs              5 µs             0~10 ms（抖动源）
```

**唯一的抖动来源是 flush 定时器的 10 ms 周期。** 下游的关节伺服不需要
200 Hz 的反馈，所以这个取舍是划算的：把 800 帧/s 的话题流量压到 100 帧/s，
同时让四个关节的位置来自同一个 CAN 反馈周期（`MotorStateArray` 的四个元素
是同批次的，而不是四次不同时刻的采样）。

### 3.3 相机同步（唯一需要硬件保证的路径，**由队友实现**）

相机固定安装在工作台上方俯视（eye-to-hand）：相机与基座之间没有相对运动，
但**手眼关系仍然要标定**，而且锁存关节位置的机制一个都不能少。

```
相机 SYNC 上升沿
   │
   ├─ EXTI ISR：读 DWT 周期计数（<0.3 µs）
   │             与上一沿求差得帧间隔
   │             读 g_motors[i].fb_position ×4（float 对齐读，原子，<0.5 µs）
   │             置 latch_pending
   │
   └─ 返回；控制环不受影响
   
下一个 20kHz ISR 边界：
   把 latch 拷到影子缓冲（双缓冲，防止被下一个 SYNC 覆盖）
   发 5 帧 CAN：sync_evt + latch×4

PC 侧：CameraSync 与图像按帧号/时间戳配对 → /camera/sync_joint_states
```

**EXTI 到锁存的偏差 < 1 µs**，这部分是硬件级的。真正的误差来自
相机自身的"同步沿 → 曝光开始"延迟以及后续的读出/USB 传输，
这部分由 `camera_trigger` 节点在线测量并发布在 `exposure_delay` 里。

**相机固定了，为什么还要锁存关节位置？** 因为视觉伺服过程中末端一直在动，
必须能回答"这一帧图像拍下时，末端到底在哪儿"。如果让 PC 收到 SYNC 通知后
再回来查关节位置，中间隔了至少一次 CAN 往返（~150 µs）+ 一次 ROS 通信
（~100 µs）+ 调度延迟。以 J3 的 2.5 rad/s 限速算，250 µs 对应约 0.63 mrad
的关节角，折算到 0.24 m 半径处大约是 0.15 mm 的末端偏差 —— 单次看不大，
但它的方向和速度同相，会直接混进视觉伺服的反馈里，表现为"越靠近目标抖得越厉害"。
更麻烦的是这段延迟本身有几十微秒到几毫秒的抖动，标定出来的手眼关系永远对不齐。
把锁存放进 EXTI ISR 之后，图像与关节位姿是**同一个硬件时刻**的，误差只有 1 µs。

## 四、为什么这么分层

### 4.1 关节伺服跑在 MCU，不跑在 PC

USB-CAN 的单向延迟就有 20~100 µs，加上 PC 的调度抖动（即使打了 PREEMPT_RT
也是几十微秒级），网络往返一次就是百微秒量级。而电流环周期是 50 µs。
在 PC 上做电流环意味着每个周期都要等一次网络往返 —— 那已经不是闭环了。
所以三环（电流 20 kHz / 速度 1 kHz / 位置 1 kHz）全部留在板内，上位机
只把 arm_control 解出来的**关节目标位置**按 100 Hz 发下去。

### 4.2 PC 只给任务级指令

PC 给的是**末端位姿**（`/arm/target_pose`，x/y/z/φ），不是关节电流，也不是
关节目标位置本身 —— 关节目标位置由 arm_control 用 D-H 正逆解算出来，
再变成 100 Hz 的 `CLS_MOTION` 关节位置指令。这样即使 PC 卡顿 100 ms，
机械臂仍然按最后收到的关节位置指令稳稳停着（直到 300 ms 看门狗超时才停机）。

### 4.3 为什么轨迹规划放在上位机、伺服环放在板内

分工的界线是"够不够得着整条手臂的模型"：

- **逆解、五次多项式、笛卡尔直线路径属于任务级。** 解逆解要知道 a1/a2/a3/d1
  与关节限位的关系，规划笛卡尔直线要在整条路径上反复解逆解并做时间标定，
  判断"目标在不在工作环带里"。这些都需要一个完整的机构模型与几何关系，
  而模型是随时会改的（换一根大臂、改丝杠导程），放在 PC 上能用 C++ 直接
  迭代，改完重新编译节点即可。
- **20 kHz 电流环属于器件级。** 它只关心一相绕组的电流跟随，与机械臂长什么
  样完全无关，理应贴着功率级跑。
- 中间用 **100 Hz 的关节位置指令**连接：上位机每秒给 100 次"三个回转轴转到
  多少弧度、升降轴到多少米"，板内插值、前馈、伺服跟随。一旦这条链路断了
  超过 300 ms，看门狗兜底主动停机。

把规划放到 PC 还有个现实好处：主机侧可以脱离 ROS、脱离硬件跑回归测试
（见 `07_kinematics.md`），几千种位姿的真机验证压缩成一次 `colcon test` 之外
的秒级检查。

### 4.4 自定义协议而不是 CANopen

见 `02_can_protocol.md` 开头。总线上只有 2~3 个节点，CANopen 的对象字典
与 NMT 状态机带来的复杂度与收益完全不成比例。

## 五、故障传播链

故障处理遵循 **"越靠近硬件，反应越快"** 的原则，分三层：

| 层 | 触发条件 | 反应时间 | 动作 |
|---|---|---|---|
| L1 硬件 | 驱动器过流 / 过温 / 母线欠压 | < 2 µs | DRV8323 内部关断，nFAULT 拉低 |
| L2 固件 ISR | 软件过流背影、越界角度跳变 | 50 µs ~ 1.5 ms | 关 PWM、置 `MSTATE_FAULT`、上抛 CAN 事件 |
| L3 固件主循环 | 温度、母线、编码器连续错误 | 1 ms ~ 20 ms | 同上 + 写 Flash 日志 |
| L4 上位机 | 心跳超时（500 ms） | 500 ms | 报警 + 诊断 + 让任务层停车 |
| L5 驱动板看门狗 | 上位机指令静默（300 ms） | 300 ms | **主动**四关节安全停机 + 气泵停 + 相机停 |

注意 L5 的方向：是**驱动板不信任上位机**，而不是反过来。
这样即使 PC 死机 / 网络断开 / ROS 崩了，机械臂也不会按最后一条指令
一直跑下去（也不会在某个关节还在动的时候把其余关节撒手）。这是安全设计里
最重要的一条。
